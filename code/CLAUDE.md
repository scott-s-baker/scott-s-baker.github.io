# Prism DIA — Claude Project Brief

## What this is

Prism is a PMM Decision Intelligence Agent for IBM FlashSystem EMEA. It ingests
market signals (buyer reviews, analyst RSS, press, competitor scrape), clusters
them into patterns with ML, and forces binary positioning decisions with SLA
deadlines and outcome tracking.

**Status:** Live · June 2026 · multi-developer (Stan / Scott on GUI design versions)

### Staging environment (added 2026-07-08)

Two deploy targets now exist, mapped by branch:

| Branch | Environment | Host | Path |
|--------|-------------|------|------|
| `main` | prod | `192.168.1.104` | `/opt/prism` |
| `develop` | staging | `192.168.1.126` | `/opt/prism-staging` |

Deploy with `./deploy.sh staging` or `./deploy.sh prod` — the script pulls
the mapped branch on the mapped host, validates `main.py` parses, brings
the stack up with the right compose override, and checks `/health`.

`docker-compose.staging.yml` and `docker-compose.prod.yml` are overrides
applied on top of the base `docker-compose.yml` (`docker compose -f
docker-compose.yml -f docker-compose.<env>.yml up -d`) — **the base file is
never edited**, it stays the field-by-field-verified source of truth for
prod. Staging gets its own container names (`prism-staging-*`), its own
Docker network (`prism_staging_default`), and its own Postgres/Weaviate/
Prefect volumes (`prism_staging_pgdata`, `prism_staging_weaviate_data`,
`prism_staging_prefect_data`) — **entirely separate instances from prod,
never shared.** This isolation exists specifically because this project has
destructive recovery playbooks (`POST /admin/reset-patterns`, deleting and
rebuilding the Weaviate `PrismSignal` class) — running one of those against
what you thought was staging but was actually prod, because they shared a
database, is exactly the failure mode this setup prevents.

`.env.staging` (on `192.168.1.126`, at `/opt/prism-staging/.env.staging`)
and `.env.prod` (on `192.168.1.104`, at `/opt/prism/.env.prod`) are created
**manually, per-host, over SSH** — never committed (both are in
`.gitignore`), never generated by tooling, and Claude should never create
even a placeholder version of either file in this repo.

### Container topology (CRITICAL — read before touching anything)

```
prism-api        — FastAPI app, port 8000
prism-postgres   — Postgres 16, port 5432, container name "postgres" on network
prism-weaviate   — Weaviate 1.27.0, port 8080/50051
prism-prefect    — Prefect 3, port 4200
```

**`prism-api` is NOT a self-contained image with code baked in.** It runs via a
**bind mount**:
```
/opt/prism/app  →  /app   (rw)
/opt/prism/config → /app/config  (rw)
```

This means **the container has no code of its own** — it reads `main.py` and
everything else live off the LXC's `/opt/prism/app` directory on every restart.

**THE #1 WAY TO BREAK PRODUCTION:** running `rm -rf /opt/prism` or
`mv prism prism_old` while the container is running. The container will keep
serving from cached file handles for a while, looking healthy — then the moment
it restarts (`docker restart`, `docker exec`, a crash, anything), uvicorn tries
to re-import `main` from the now-empty bind-mounted directory and fails with
`Could not import module "main"`, looping forever. This happened once already
during a "let's redeploy cleanly" attempt — never delete `/opt/prism` while
`prism-api` is up. If you need to swap code, copy new files in, don't delete
the directory tree first.

**Network:** containers talk to each other via the `prism_default` Docker
network using service names — Postgres is reachable as `postgres:5432` from
inside containers, not `192.168.1.104:5432`.

**Env vars the running container has** (defined in the committed
`docker-compose.yml`, cross-validated against `docker inspect prism-api`):
```
PG_USER=prism  PG_PASSWORD=prism  PG_DB=prism  PG_HOST=postgres  PG_PORT=5432
LLM_PROVIDER=ollama  OLLAMA_MODEL=llama3.1:8b  OLLAMA_BASE_URL=http://192.168.1.121:11434
WEAVIATE_URL=http://weaviate:8080
EMBED_MODEL=sentence-transformers/all-MiniLM-L6-v2

ANTHROPIC_API_KEY=    (empty — Ollama is default provider)
CLAUDE_MODEL=claude-sonnet-4-6   (set but unused while LLM_PROVIDER=ollama)
```

**docker-compose.yml is now committed to the repo root.** It reproduces the

No env var needs to be retyped from memory or guessed again.

### THE BABEL STANDALONE GOTCHA (cost ~2 hours of debugging — read this twice)

There is a flash-prevention `<script>` tag that sets `data-theme` and
`data-design` attributes before React mounts (avoids a flash of wrong
theme/colors on load). **It must be placed INSIDE `<head>`, before
`</head>`.** If it ends up between `</head>` and `<body>` (invalid HTML
nesting), browsers silently re-parent it into `<body>` — but Babel
Standalone's `transformScriptTags` scanner walks the DOM in document order
*before* that re-parenting settles, and throws:

```
Uncaught SyntaxError: Failed to execute 'appendChild' on 'Node':
Cannot use import statement outside a module
    at transformScriptTags.ts:114
```

This error is **misleading** — there is no `import` statement anywhere in the
file. It's a side effect of Babel's scanner getting confused by the malformed
script nesting. The fix is structural, not content-related:

```html
<!-- WRONG — caused the bug -->
        </style>
    </head>
    <script>...</script>
    <body>

<!-- CORRECT -->
        </style>
        <script>...</script>
    </head>
    <body>
```

Verify with: `grep -n "</head>\|<body>" app/gui/index.html` — `</head>` and
`<body>` should be on consecutive lines with nothing between them.

**Second gotcha, same family:** never use `<>...</>` (JSX fragment shorthand)
inside an IIFE `(() => { ... })()` embedded in JSX. Babel Standalone fails
silently on this (blank page, no console error) in some cases. Use
`<React.Fragment>...</React.Fragment>` explicitly inside any IIFE. Top-level
component `return (<>...</>)` is fine — the bug is specific to fragments
nested inside function-call expressions inside JSX.

### Always verify before declaring a GUI edit done
```bash
python3 -c "
txt = open('app/gui/index.html').read()
jsx = txt[txt.find('text/babel'):txt.rfind('</script>')]
print('braces:', jsx.count('{') - jsx.count('}'))
print('parens:', jsx.count('(') - jsx.count(')'))
print('head/body adjacent:', '</head>\n    <body>' in txt or '</head><body>' in txt)
"
```
A diff of 0/0 on both does NOT guarantee correctness (string literals can hide
mismatches) but a non-zero diff guarantees a problem.

```
                              recover. The admin endpoint is deliberately safe.
```

## Signal quality design (do not change without updating tests)

```python
# Independence weights
"analyst": 1.0   "field": 1.0   "press": 0.5   "competitor": 0.25

# Recency decay
field/analyst  → SLOW: 30d@1.0, 90d@0.75, 180d@0.5, >180d floor 0.25 (never archived)
press/competitor → FAST: 7d@1.0, 21d@0.75, 60d@0.5, >60d archived (0.0)

# Tier thresholds
EMERGING     weighted_count >= 2.0, 1+ source categories
CONFIRMED    weighted_count >= 3.0, 2+ source categories
ESTABLISHED  weighted_count >= 5.0, 3+ categories, sustained 30+ days
```

Signal dedup: `id = sha256(source | source_family | normalize_content(content))`.
`normalize_content` lowercases + collapses whitespace. `ON CONFLICT DO NOTHING`.

**Known cleanup performed once:** 400 duplicate signals existed from before
this normalization was deployed (e.g. blocksandfiles.com had 150 rows for 81
unique articles). Cleaned via:
```sql
DELETE FROM signal WHERE id NOT IN (
  SELECT DISTINCT ON (source_family, content) id FROM signal
  ORDER BY source_family, content, created_at ASC
);
```
Followed by a full Weaviate collection rebuild (`DELETE` the `PrismSignal`
class, re-run `/embed`) and re-cluster. If signal counts ever look inflated
again, this is the playbook.

## Known historical bugs already fixed — do not reintroduce

1. **Cursor reuse in `get_patterns()`** — the per-pattern signal-sample lookup
   was sharing a psycopg3 cursor with the outer pattern loop, silently
   breaking iteration. Fixed by fetching all pattern rows first, then opening
   a fresh cursor per signal lookup. Also `ANY(%s)` → `ANY(%s::text[])` for
   passing Python lists to Postgres array params.
2. **PeerSpot Pure Storage URL** — rebranded `pure-storage-flasharray-reviews`
   → `everpure-flasharray-reviews`. If `/ingest/peerspot` 404s on Pure, check
   if PeerSpot renamed something else too.
3. **Ollama health was hardcoded amber** — `/health` now does a real
   `httpx.get(f"{OLLAMA_BASE_URL}/api/tags", timeout=3.0)` liveness check.
4. **Demo data silent fallback** — GUI used to serve ~500 lines of mock data
   on any API failure, setting `window.__PRISM_DEMO = true`. Fully removed.
   API failures now surface as real errors in the UI.
5. **Stale patterns after Weaviate rebuild** — after deleting duplicate
   signals and rebuilding the vector store, old patterns referencing
   now-deleted signal IDs lingered. `POST /admin/reset-patterns` then
   `POST /cluster` is the correct recovery sequence.
6. **`restore_assumption` never worked** — `delete_assumption` comments out
   the id line as `# - id: X` (dash included), but `restore_assumption` was
   matching on the substring `# id: X`, which never occurs. Every restore
   call silently failed with "Assumption not found or not deleted" since
   the endpoint was written. Fixed 2026-07-02 by matching on the
   `# DELETED: <date>` marker instead and reconstructing indentation
   explicitly. All four `/assumptions` write endpoints (create, update,
   delete, restore) now also append a change-log entry, previously only
   create/update did.
7. **`docker compose up -d` recreate silently switched to empty volumes**
   — docker-compose.yml's `volumes:` block declared `prism_pg_data` etc.
   without `name:`, so Compose auto-prefixed with the project name →
   `prism_prism_pg_data`, a brand-new empty volume distinct from the
   original hand-created one holding real production data. First recreate
   after committing the compose file dropped `/health`'s `signal_count` to
   0 (data was never touched, containers just pointed at the wrong
   volume). Fixed by adding explicit `name:` + `external: true` to all
   three volume declarations, pinning them to the pre-existing volume
   names. **Any docker-compose.yml describing an already-running,
   hand-created stack must pin volume names explicitly** — this is not
   optional, the first recreate will silently fork onto fresh volumes
   otherwise.

## Git + Deploy workflow (Mac → GitHub → LXC, since 2026-07-02)

**Never do this on the LXC:**
```bash
rm -rf /opt/prism   # while prism-api is running — kills the bind mount source
```

**Step 1 — commit and push from the Mac (local, unprompted per settings.json):**
```bash
cd /Users/stan/Documents/Prism
git add -A
git commit -m "feat|fix|docs: description"
git push
git tag v1.X && git push origin v1.X    # for releases
```

**Step 2 — pull onto the LXC:**
```bash
ssh root@192.168.1.104 'cd /opt/prism && git pull'
```

**Step 3 — verify structurally before touching the container:**
```bash
ssh root@192.168.1.104 'python3 -c "import ast; ast.parse(open(\"/opt/prism/app/main.py\").read()); print(\"OK\")"'
```

**Step 4 — restart only if `app/*.py` changed (GUI-only changes need no
restart, `app/gui/index.html` is served straight off the bind mount):**
```bash
ssh root@192.168.1.104 'docker restart prism-api'
sleep 8   # restart is not instant — curl immediately after will fail with
          # "Expecting value: line 1 column 1" — this is NOT a real failure,
          # just re-run the check after a few seconds
ssh root@192.168.1.104 'curl -s http://localhost:8000/health'
```

**Always verify the live file hash matches what you expect before debugging
further:**
```bash
curl -s http://192.168.1.104:8000/ | md5   # from the Mac
```
Compare against the local file's hash. If they match and the page is still
blank, the bug is genuinely in that file's content/structure, not a deploy
problem — stop checking deploy steps and start checking the file itself.

GitHub (`github.ibm.com/hrvoje-stanilovic/prism`) remains the verified source
of truth — the Mac clone and the LXC should both trace back to it exactly;
if either drifts, `git log -1` on both sides is the first thing to check
(see the Development environment section above for the diff command).
